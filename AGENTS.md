# Desenvolvimento

Esta é a nova aplicação independente no repositório lmdsistemas-lmd/quadrinha. Trabalhe neste checkout (/workspace/quadrinha no ambiente atual). O REA é uma ferramenta separada em /workspace/reamy; não modifique seu código para desenvolver este sistema. Use o checkout/workspace existente; não crie Git worktrees sem pedido explícito.

Use Node 24.18.0. Instale com npm ci; Nodemailer é usado para SMTP com TLS. O padrão npm start inicia platform.mjs (SaaS com três áreas). Leia docs/PLATAFORMA.md. Use npm run platform:admin apenas no terminal local para criar o superadministrador sem senha padrão. Não há criação pública desse papel. Comandos: npm run start:standalone (banco anterior), npm start (SaaS); npm run db:operational (cria destino novo sem substituir); npm run start:operational; npm run check; npm test. O servidor padrão escuta em 127.0.0.1:3000 e o SaaS usa data/platform/. O modo start:standalone usa data/quadrafacil.sqlite. Não apague nem substitua o banco principal para testes; use QF_DATABASE_PATH ou createApp({databasePath}) apontando para um banco temporário.

O usuário inicialmente escolheu demonstração e agora autorizou iniciar operação real: use banco operacional separado, preserve as contas de acesso locais e o banco anterior, sem copiar os registros fictícios. Veja docs/BANCO-OPERACIONAL.md e docs/MERCADO-PAGO.md. Não migre dados do sistema original, não grave nele nem reutilize suas credenciais na nova aplicação. Nunca exiba ou salve valores dos segredos. Capturas originais autenticadas ficam em /workspace/scratch/quadrafacil e não devem ser incluídas em public/.

Consulte docs/ESCOPO.md para distinguir implementação local e equivalência ao original. Mantenha limitações visíveis e não simule pagamento, nota fiscal, envio de mensagens ou integração como concluídos. Preserve as regras de conflitos e atomicidade das recorrências, estoque e recebimentos sem duplicação. Execute testes relevantes após mudanças. A validação visual inicial fica em docs/ e usa apenas dados fictícios.

No SaaS, o superadministrador é criado somente por CLI local; cadastros comuns exigem e-mail verificado. No modo standalone, o primeiro administrador é criado pela tela inicial, sem senha padrão. Publicação externa exige definir destino e parâmetros próprios de hospedagem; não trate um processo local como aplicação publicada.

O proprietário tem somente acesso web ao original e agora está preparando sua aplicação operacional. Continue a reconstrução independente; execute testes somente com bancos temporários e dados fictícios. Não bloqueie o desenvolvimento pedindo código de servidor original ou homologação do original; use a referência observável e registre diferenças e regras próprias.

Mantenha os três domínios de acesso e de dinheiro separados: /admin (plataforma), /app/{arena} (gestão) e /reservar/{arena} (cliente final). Assinaturas usam somente as credenciais da plataforma; reservas usam somente as da arena. Não use credenciais globais como fallback. SQLite mestre, financeiro da plataforma e bancos de empresas são separados. Credenciais privadas usam AES-GCM e nunca devem ser devolvidas ao navegador; testes externos usam transportes fictícios explicitamente identificados. Não realize cobranças nem envios reais para validar desenvolvimento.
